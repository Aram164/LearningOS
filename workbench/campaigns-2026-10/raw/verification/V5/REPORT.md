## Findings

1. **`npm run stage-plugin` — a generator WORKFLOWS §31 names for the
   backup precondition does not exist.**
   `system/WORKFLOWS.md:988` says the UI's `plugin/build-info.json` is
   "generated by `npm run stage-plugin` or `npm run build` in
   obsidian-ui". At the pinned UI checkout `npm run stage-plugin` exits 1
   with `Missing script: "stage-plugin"`; `git log --all -S"stage-plugin"`
   over the UI repository returns nothing, so the script never existed.
   `npm run build` works and produces the file (and the rebuilt plugin
   outputs are byte-identical to the committed ones). Evidence:
   `findings/stage-plugin-not-a-script/` (probe + finding), transcript in
   `logs/stage-plugin-probe-output.log` and
   `logs/stage-plugin-missing-script.log`. Certainly wrong: the first half
   of the sentence. Scope note inside the finding: the claim sits in the
   workflow the V5 procedure transcribes, and the drill's backup refusal
   makes it load-bearing.

## Observations (no contract line violated; recorded because they matter to an operator)

- **Materials mount state decides whether a materials-less restore passes.**
  The faithful restore carries the backup's (empty) materials directory; a
  mounted-but-empty tree turns the clone's 518 unresolvable material
  references into hard `MATERIAL-MISSING` errors, so the documented full
  verify cannot pass on this machine. Without the directory (materials
  unmounted), the same verify is all green and the loss is named only as
  `MATERIALS-OFFLINE`/`MATERIALS-DRIFT` warnings. Both behaviors are
  truthful — errors for "mounted and missing", warnings for "not mounted" —
  but a recovery on a machine without materials needs to know that
  deleting the restored empty `materials/` directory flips full verify from
  red to green without changing a single canonical byte.
- **The `unaccounted` check is allowlist-bounded by design.** A planted
  file inside the declared trees is caught (attack 3); a stray file at the
  core root or under an excluded name (`generated/`) passes verify
  unmentioned (attacks 3b/3c). `backup-roots.yaml` states the allowlist
  semantics explicitly; nothing outside the declared boundary is claimed.
- **`backup-manifest` does not consult material references or
  `local-attachments.yaml`.** A damaged materials tree or absent
  attachments still back up cleanly; the integrity claims live in
  validation and in the full verify's canonical-validation step, which did
  name both losses in attacks 5 and 6. Division of labor, not a gap.
- **Clock-derived warnings drift.** The transcript's final fixture line
  reads `0 error(s), 14 warning(s) — OK`; re-running validate on the
  byte-unchanged fixture root later in the same morning yields 16 warnings
  (2 extra `WS-NEGLECT`, an elapsed-time advisory). Errors stayed 0.
  Warnings are documented as never blocking, so this is behavior, not a
  defect — but anyone re-deriving the transcript's warning count verbatim
  will see it move.
- **`npm run build` reproducibility.** Rebuilding the pinned UI checkout
  produced byte-identical `plugin/main.js` and `plugin/styles.css`
  (`git status` clean; `build-info.json` gitignored). Relevant to §31's
  "recovery preserves the built plugin rather than rebuilding it": at this
  pin, rebuilding is also byte-safe.

## Coverage gaps

- The five real local-only attachment PDFs (265 MB) were never available,
  so the contract's happy path — a present attachment **matching** its pin
  — was exercised only in the negative (absent → warning; different →
  error). A byte-identical file passing the pin is untested here.
- The fixture has no `.flat` layer by default, so the alias-recording path
  ran only via the constructed `source-empty` folder in attack 6B; a real
  alias farm as in `LearningOS/materials` (symlink names that are not the
  target's folder name) was not reproducible from the fixture.
- `ui-install-preflight` and `ui-bundle-smoke` ran the restored installer
  and `node --check` — they passed — but the restored bundle was never
  opened in Obsidian (the full verify itself reports
  `manual_ui_open_required: True`; that human step remains, by design).
- Scrut was not installed (that is `make setup`'s job), so the transcript
  was executed block-by-block in bash rather than by `scrut test`. Every
  block's expected output was compared by hand; a Scrut-runner mismatch
  (if any) would not have been observed.
