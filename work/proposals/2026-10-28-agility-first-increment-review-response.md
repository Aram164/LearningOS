## Accepted

- **Separate migration acceptance:** Stage 4 now has 4A inventory/dry-run specification, 4B fixture-based Core migration, and 4C UI consolidation/domain retirement. Each has an explicit deliverable and acceptance boundary; Project removal cannot precede preservation and normal-access evidence.
- **Reverse aliases and historical compatibility:** inventory and test old Project IDs, nested IDs, workspace references, generated identities and historical receipts. The current alias schema and validator accept Project targets; Module targets need a deliberate contract change, not an alias-file hand edit. Owners: `system/schema/project-aliases.schema.json`, `tools/learning_os/derive/validation/projects.py`, `tools/learning_os/derive/projection/projection/records_projects.py`.
- **Controlled Module visibility:** the UI's `openAcademicModules()` and Core's `is_listed()` currently exclude `kind: project`. Any change must agree across Core/UI and prove the inclusion of intended ordinary Modules and exclusion of closed, compatibility-only, quarantined and boundary records. Owners: `obsidian-ui/src/manifest-store.ts`, `tools/learning_os/derive/semesters.py`.
- **Operational preservation:** workstreams, open research questions, relationships with their reasons/contributions, files and access boundaries must remain reachable through ordinary Module/workspace navigation and search. Retaining their original bytes only as migration evidence does not satisfy this gate.
- **Academic meaning:** 4A must settle kind and metadata before migration. `system/schema/module.schema.json` and `tools/learning_os/derive/validation/curriculum.py` require institution and semester for academic Modules. `tools/learning_os/derive/projection/projection/lifecycle.py` derives enrollment for active academic Modules, so changing the kind merely to appear in Modules can introduce an unsupported administrative claim. Current `work/COORDINATION.md` and the thesis workspace explicitly defer registration/deadline facts until they are known; neither the compatibility Module nor the active Project supplies credits or grade. Do not invent those values or treat unknown credits as zero. **ASSUMPTION:** the review's reference to degree-credit accounting implies a consumer beyond the display paths inspected so far; 4A must verify any such consumer before claiming preserved accounting behavior.
- **Clean-commit reproduction:** reran the unmodified benchmark from clean first-increment commit `d32d2cf8c25d3115740939962cbd1e0c7b3e152b`, before editing review documents. All five runs passed; input bytes, reproduced-record counts, validation counts, intended file changes, package hashes and receipt counts match the initial results. Source hashes were checked against the clean tree. Retained [raw reproduction](../../workbench/agility-experiment/baseline-clean-d32d2cf8.json) and [provenance](../../workbench/agility-experiment/baseline-clean-d32d2cf8-provenance.json); the original baseline remains intact. Timings are observations, not equivalence criteria.
